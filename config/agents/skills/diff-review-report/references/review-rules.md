# レビュー規範

`diff-review-report` スキルの下でレビューを行うサブエージェントが従う規範。1段階目（plan非開示）・2段階目（plan照合）の両方に適用する。

## 1. グループ化

- ファイル単位ではなく **「1つの意図」単位** でまとめる。例: リネームとそれに伴う import 修正は1グループ。機械的な追従変更（型定義の追従修正など）は本体グループに吸収する。
- 各グループに `intent`（なぜこの変更をしたのか、1〜2文）を必ず書く。
- **intent が差分から読み取れない場合は書き繕わず `unclear: true` を立て、「要改善: 意図が読み取れない」として扱う。** 無理にもっともらしい意図をでっち上げない。

## 2. 並び順

- ファイル名順・パス順で並べない。**リスク順**（`risk: high` → `low`）で groups を並べる。
- リスク判定基準:
  - **high**: 実行時の振る舞いが変わる / 共通基盤・広範囲に効く / 外部I/O・認証・権限・金銭に触る / テストで守られていない
  - **medium**: 上記のいずれかに部分的に該当するが影響範囲が限定的
  - **low**: 純粋な整形・コメント・docs・テストのみの変更など

## 3. 指摘の粒度と severity

- `blocker`: 壊れる・データが壊れる・セキュリティ上の問題。
- `warning`: 動くが設計上の欠陥・将来の事故要因になりうるもの。
- `note`: 改善提案・好み寄りのもの。
- 好みだけの指摘は `note` 止まりにする。**`blocker`/`warning` は必ず「失敗する具体シナリオ（入力 → 誤った結果）」を `body` に含める。** 抽象的な懸念だけで severity を上げない。

## 4. 各指摘の必須項目

- 場所（ファイル + 新/旧の行番号 + hunk ID）
- 指摘本文（`body`）
- 改善案（`suggestion`）— **改善案が書けない指摘は出さない。**

## 5. 忖度の禁止

- 「planに書いてあるから妥当」は **1段階目には存在しない前提**（1段階目は plan を渡されていないので、そもそも判断材料にできない）。
- 2段階目でも `demoted` に落とすだけで指摘を消してはいけない。`resolved`（誤読だった場合のみ）で初めて指摘を取り下げてよい。
- 「LGTM」だけの結論を出さない。**指摘がゼロなら、なぜゼロと判断したか（確認した観点）を `summary` に書く。**

## 6. 推測の禁止

- 差分に写っていない前提（呼び出し元の挙動、他モジュールの実装など）に依存する指摘は、**実際にファイルを読んで確認してから出す。**
- 確認できない場合は `note` にして「未確認」と明示する。裏取りしていない推測を `blocker`/`warning` にしない。
