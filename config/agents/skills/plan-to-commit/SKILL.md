# plan-to-commit

plan 作成 → 実装 → レビュー確認 → 修正 → コミット、を5フェーズで回すオーケストレーション用スキル。各フェーズは別セッション・別ツール（Fable / Codex / Claude Code など）で実行されることがあるため、**必ず現在地判定から始める**。

## 現在地の判定手順

作業を始める前に、以下の順でリポジトリの状態を確認し、どのフェーズから再開するかを決める。

1. `plans/` ディレクトリに対象の plan ファイルがあるか確認する。無ければ **フェーズ1** から。
2. plan がある場合、`git status` / `git diff` で plan に対応する実装差分が存在するか確認する。差分が無ければ **フェーズ2** から。
3. 実装差分がある場合、レビュー用 HTML（既定はリポジトリルートの `review-<slug>.html`。無ければ `/tmp` 配下も見る）が生成済みかを確認する。無ければ **フェーズ3** から。
4. レビュー HTML があり、user からのフィードバック markdown をまだ受け取っていなければ、**フェーズ3の出口条件待ち**（user 入力待ち。勝手に進めない）。
5. フィードバック markdown を受け取っている、またはこれから受け取る場合は **フェーズ4** から。
6. フィードバック対応が完了し検証も通っていれば **フェーズ5** へ。
7. plan ファイルが既に削除され `git status` がクリーンなら、このスキルの作業は完了している。

各フェーズの詳細は以下。

## フェーズ1: plan を書く

**入口条件**: これから着手する変更について、plan がまだ存在しない。

**やること**:
- 出力先は **リポジトリルートの `plans/<slug>.md`**。slug は kebab-case（例 `plans/fix-context-only-flag.md`）。
- `.gitignore` を確認し、`plans/` と `review-*.html`（フェーズ3のレビュー画面出力。既定はリポジトリルート直下の `review-<slug>.html`）が**それぞれ**記載済みか確認する。無い分だけ追記する（重複追記しない）。多くのリポジトリでは両方とも未記載で、`plan.md` や `*.html` が「未追跡だが ignore もされていない」状態になり `git add -A` 等で誤って拾われるため要注意。追記した場合は変更内容として user に伝える。
- 書式は `references/plan-format.md` に従う。
- plan を書き終えたらファイルパスを user に伝え、**内容を読んでもらう**。要約を数行で口頭報告し、特に「やらないこと」と「方針」で判断が割れそうな箇所を名指しで挙げる。
- user が plan にインラインでメモを書き込んで返してくることがある。その場合は**全てのメモに対応してから**再提示する（承認まで反復する）。

**出口条件**: 「何を・なぜ・どう検証するか」が読み手に伝わり、変更対象ファイルの見当がついている。曖昧な項目が残るなら user に確認してから次へ進む。**user が plan に合意している**（「これでいい」「実装して」等）。合意なしにフェーズ2へ進まない。

## フェーズ2: 実装

**入口条件**: フェーズ1の出口条件を満たす plan が `plans/<slug>.md` に存在する。

**やること**:
- plan の「変更計画」を上から順に実装する。**plan に無い変更を混ぜない**。必要になったら先に plan 側を更新してから実装する。
- テストがあるプロジェクトでは、plan の「検証」に書いたコマンドを実装中に回す。
- プロジェクトの `CLAUDE.md` / `AGENTS.md` に実装の委譲規約（サブエージェントに実装させる等）がある場合はそれに従う。

**出口条件**: plan の全項目が実装済み、または未着手項目が plan 上に明示されている。ビルド/型チェック/テストが通っている。

## フェーズ3: レビュー画面で確認

**入口条件**: フェーズ2の出口条件を満たしている（実装差分が存在する）。

**やること**:
- **`diff-review-report` スキルを呼ぶ**（Skill tool で `diff-review-report` を invoke する）。plan のパス（`plans/<slug>.md`）を渡す。
- 呼び出し先のスキルが「plan非開示の1段階目 → plan照合の2段階目 → 単一HTMLレポート生成」を行う。
- 出力先は既定で **リポジトリルート直下の `review-<slug>.html`**（`.gitignore` 済み）とする。同じ plan で再レビューしても同じパスに上書きされ、ブラウザで開くパスが安定するため。リポジトリを一切汚したくない場合は `/tmp` 配下に出す代替でもよい。
- 生成された HTML の絶対パスを user に伝えて開いてもらう。
- **ここで待つ。** user がレビュー画面で採用/却下・コメントを付けて「フィードバックmarkdown」を貼り戻すまで、勝手に修正を始めない。

**出口条件**: user からフィードバック markdown（または「指摘なし」の返答）を受け取っていること。

**Codex を使う場合の事故防止手順（`diff-review-report` が内部で Codex を呼ぶ場合を含む）**:

> 実際に起きた事故: `codex exec review` を `--dangerously-bypass-approvals-and-sandbox` 付きで実行したところ、read-only のはずのレビュー中に未追跡の `plan.md` が削除された。bypass フラグは shell コマンドを非サンドボックスで実行するため、レビューでもファイルを破壊しうる。**このフローの成果物（`plans/<slug>.md` とレビューHTML）はどちらも未追跡ファイルなので、再発条件に完全一致する。**

- Codex にレビューさせる前に `cp plans/<slug>.md /tmp/plans-backup-<slug>.md` で退避する。
- `--dangerously-bypass-approvals-and-sandbox` は使わない。既定サンドボックス（または明示的 read-only）で実行する。
- 正しい起動形は `bunx @openai/codex exec review --base develop`（`codex` は PATH に無い。codex-cli 0.138.0 で確認）。**`--base <branch>` とカスタムプロンプトは併用不可**なので、独自のレビュー観点を渡したいときは `--base` を使わず `bunx @openai/codex exec "<prompt>"` の形にする。
- Codex 実行後に `ls plans/` で plan が残っていることを確認する。

## フェーズ4: 修正と動作確認

**入口条件**: フェーズ3の出口条件を満たしている（フィードバックを受け取っている）。

**やること**:
- 受け取ったフィードバックの各指摘について、**まず妥当性を自分で吟味する**。鵜呑みにせず、妥当でないと判断したものはその理由を述べて対応しない。
- 対応した指摘・見送った指摘・その理由を一覧で user に報告する。
- 修正が plan の方針を変える規模なら、plan ファイル側も更新する。
- 検証コマンド（lint / format / type-check / test / build）を回して結果を報告する。**失敗しているのに完了と言わない。**

**出口条件**: 検証が通っている、または落ちている項目とその理由が user に報告されている。

## フェーズ5: コミットして plan を消す

**入口条件**: フェーズ4の出口条件を満たしている。

**やること**:
- **ブランチ確認を最優先**: `develop` / `main` などの共有ブランチに直接コミットしない。共有ブランチ上なら、まず `git switch -c <type>/<slug>` でブランチを切る（起点は `origin/develop` など、プロジェクトの既定ベース）。
- コミットメッセージは `references/commit-handoff.md` の変換ルールで plan から組み立てる。Conventional Commits の subject + plan 由来の本文。
- レビュー HTML（`review-*.html`）や plan ファイルはコミットに含めない。
- コミット後に `plans/<slug>.md` を削除する（`rm`）。**コミットが成功したことを確認してから消す**（`git log -1 --stat` で確認）。
- push は user の明示的な指示があるまで行わない。

**出口条件**: コミット済み・plan 削除済み・`git status` がクリーンであることを確認して報告。

## 全体の注意

- 各フェーズの区切りで user に短く報告し、勝手に次のフェーズへ突き進まない（特にフェーズ3→4、4→5）。
- レビューHTML（`review-*.html`）をコミットに混ぜないこと。既定はリポジトリルート直下の `review-<slug>.html` を `.gitignore` 済みにして出力する（リポジトリを一切汚したくない場合は `/tmp` 配下に出す代替も可）。
- plan ファイルをコミットに含めない。

## 関連スキル

- `diff-review-report` — フェーズ3で呼ぶ本体。plan非開示→plan照合の2段階レビューとHTMLレポート生成を担う。
- `tdd` / `tidying` — フェーズ2の実装中に従う開発サイクル（Red-Green-Refactor、構造変更と振る舞い変更の分離）。
- `git-commit` — フェーズ5のコミットメッセージ作法。プロジェクトによっては `/git:commit` コマンドに委譲されている場合がある。
- `issue-plan` — **GitHub Issue から plan を作る別スキル**。`docs/issues/ISSUE-<番号>/plan.md` に出力する点が本スキルの `plans/<slug>.md` と異なる。GitHub Issue 起点の作業では `issue-plan` を使って plan を作成し、**本スキルのフェーズ1をスキップしてフェーズ2から入る**。この場合、フェーズ5で削除対象を取り違えないこと。`docs/issues/` 配下の plan は成果物としてリポジトリにコミットされている場合があるため、`plans/<slug>.md` と異なり **削除しない**（`issue-plan` 側の運用に従う）。
